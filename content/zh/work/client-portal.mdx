## 背景

以前，俱乐部订了定制队服之后，只能靠邮件追进度：设计稿批了没有，报价单在哪，什么时候发货。每回答一个问题，都得有销售去 CRM 里查一遍。下单表单、审批环节和设计稿散落在不同地方，各有各的链接。

## 约束

- **CRM 仍是唯一可信的数据源。** 商机阶段、报价和联系人早就都在 CRM 里；门户不能变成第二个数据库。
- **不用密码。** 队服负责人每个赛季都会换人，所以只凭一个邮箱地址就得能登录。
- **两个品牌。** 同一个门户服务不止一个店铺品牌，每个品牌有自己的外观。

## 我的角色

规划是我写的。我搭出了门户的第一版（认证、仪表盘、订单列表、订单详情），并把原有的下单表单迁了进来。之后大部分功能开发由另一位工程师接手，我负责集成和 n8n 这一侧。

## 架构

- **前端**：React 19、TypeScript、Vite、Tailwind 加 shadcn，用 TanStack Query 管理服务端状态，用 React Router 组织页面。
- **登录**：通过邮件发送六位数验证码，由工作流校验，会话有效期 30 天。
- **订单**：进度阶段直接映射自 CRM 的商机阶段，门户里看到的和销售看到的完全一致。
- **下单表单**：分多步（基本信息、尺码、产品选择、确认），支持上传设计稿和审批报价，审批后生成一份已签署的审批文件。
- **后端**：自己没有。每一次读写都是一个 n8n webhook，由它去和 CRM 打交道。
- **Mock 模式**：一整套 fixture，让整个门户可以在本地脱离后端运行，用于演示和评审。

## 三个决策

**1. 用 webhook 代替 API 服务器。** 公司的运营本来就跑在 n8n 上。把门户的后端也放在那里，运营团队不用发版就能看到并修改每一个步骤。

**2. 直接展示 CRM 的阶段，不另起一套状态模型。** 如果另外设计一套更友好的状态，就得维护两套模型并让它们保持同步。直接映射现有阶段，门户展示的就始终是真实情况。

**3. 从一开始就做 mock 模式。** 每个页面都能在没有后端的情况下用 fixture 渲染出来。这样演示不会出事故，设计评审很快，另一位工程师也不需要接触线上数据就能开发。

## 成果

- 队服负责人自己就能看到每个订单和它所处的阶段，不用再发邮件问销售。
- 下单表单、设计稿、报价和审批集中在一个地方，一次登录全部搞定。
- 门户上线时，没有新增任何一台需要运维的服务器。

## 如果重来

先把 webhook 的契约定成双方共享的类型化 schema，再开始写页面。否则工作流里改了一个字段名，只能等到运行时才发现。

## 技术栈

React 19、TypeScript、Vite、Tailwind、shadcn、TanStack Query、React Router、react-hook-form、Zod、n8n、Zoho CRM、Cloudflare Pages。
