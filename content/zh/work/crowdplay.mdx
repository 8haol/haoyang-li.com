## 背景

当时我在帮忙办一场国际学生迎新活动：大约五十人，七个活动站点，分队计分，最后还有颁奖。这类活动通常靠纸质卡片加一张表格，结果就是排队、丢卡，而且谁也不知道哪队领先。我希望整个场地玩起来像是同一场游戏。

## 约束

- **只用手机。** 来宾不会装任何东西，扫二维码就要能用，在微信内置浏览器里也一样。
- **志愿者和 Wi-Fi 都靠不住。** 一晚上工作人员会换好几轮，断线重连也绝不能让分数丢失或重复记分。
- **只有一个晚上。** 线下活动没有第二次机会。

## 我的角色

全部由我负责：玩法设计、UI、数据库及其函数、投影视图、管理后台，以及活动当晚的现场执行。

## 架构

- **来宾端**：扫码加入，拿到一个三位数编号；主持人开始之前，等候页会显示他们的护照卡。
- **工作人员端**：凭六位数代码在站点给整队打分，不需要账号。
- **投影端**：实时展示各队进度、活动动态、签到墙和颁奖环节。
- **管理端**：管理组织、活动和站点库，上面还有一层平台所有者视图。
- **后端**：Supabase Postgres，启用行级安全；每个游戏操作都是一个带幂等键的 SECURITY DEFINER 函数，所以重试也不会重复计分。各个屏幕每三秒轮询一次。
- **媒体**：组织者的照片和视频相册放在 Cloudflare R2 上，通过 edge function 签发的签名 URL 访问。

## 三个决策

**1. 数据库就是游戏引擎。** 规则写进 Postgres 函数之后，测试只需要盯一个地方，不用部署服务器，所有客户端也都享有同样的保证。

**2. 用轮询，不用实时推送。** 五十部手机在场馆 Wi-Fi 上反复重连 websocket，这种故障我可不想在活动当晚碰上。三秒一次的轮询很无聊，但结果可预期。

**3. 主题就是数据。** 文案、印章和站点名称都来自主题配置，所以中秋版直接复用了整套引擎，只换了外观。

## 成果

- 迎新活动从头到尾都跑在它上面，投影上实时显示分数，最后的颁奖也在投影上进行。
- 重试天然安全：每一次计分调用都是幂等的。
- 已开源发布，并新增了一套中秋主题。

## 如果重来

写代码的同时就把志愿者指南写好。活动当晚，给志愿者一句清楚的说明，比加一个新功能管用得多。

## 技术栈

React 19、TypeScript、Vite、Tailwind、React Router、Supabase（Postgres、RLS、RPC、Edge Functions）、Deno、Cloudflare R2、Netlify。
