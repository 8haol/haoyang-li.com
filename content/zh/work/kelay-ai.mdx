## 背景

在英国，华人开的餐厅、按摩店、美甲店和宠物美容店，常常因为所有人都在忙而漏接电话。漏接一个电话，就是丢了一单预约。现有的电话机器人只会说英语，千篇一律，还得找开发者来配置。Kelay 是一个填张表就能设置好的前台。

## 约束

- **老板不懂技术。** 设置流程必须是向导，不能是配置文件；上线之前，老板还得能亲耳听到 agent 的表现。
- **到处都有重试。** 电话服务的 webhook 会重试，所以保存通话必须是幂等的：同一个事件处理两次，绝不能生成第二条记录。
- **两种语言。** 很多来电者更习惯说普通话，同一个 agent 必须同时应付英语和普通话。
- **两个创始人，没有融资。** 在试点客户开始付费之前，每个组件都必须是带免费额度的托管服务。

## 我的角色

所有技术工作都由我负责：多租户数据模型、身份认证、入驻向导、Retell agent 的开通、各个工具的实现、webhook 处理、订阅计费、商家后台，以及用来调优 agent 的测试通话。

## 架构

- **租户**：每个租户在 PostgreSQL（Drizzle）里拥有自己的门店、服务项目、员工、营业时间和预约日历。行业模板（`verticals`）会预填一套合理的默认值。
- **入驻向导**：收集商家资料，完成后自动开通一个 Retell agent，带上生成好的 prompt 和一组工具。商家上线前可以先在浏览器里打一通测试电话；Twilio 号码开通功能已经做好，正等着第一次真实运行。
- **工具**：开放给 agent 的有查询空档、预约、修改（改约或取消）、查找预约，以及餐厅的空桌查询和订座。每个工具都是一个 HTTP 端点，agent 调用时带上共享密钥。
- **通话存储**：录音、转写文本和通话结果按通话保存，以 Retell 的 call ID 为键做 upsert，所以重试的 webhook 永远不会生成第二条记录。
- **计费**：用 Stripe 做订阅和通话分钟充值。agent 的指令里明确规定绝不在电话里收款；定金功能已列入路线图。

## 三个决策

**1. 用数据生成 agent，而不是手工配置。** agent 的 prompt、声音和工具集都由租户记录生成。营业时间一改，agent 就会重新生成。正因为这样，入驻才能是填一张表，而不是一单服务项目。

**2. 在重试会落到的地方做幂等。** 电话服务商会重试 webhook。通话存储以服务商的 call ID 为键做 upsert，同一个事件处理两次也不会出问题：用一条不变式，消灭了一整类重复记录的 bug。

**3. 按实测延迟选模型。** 早期的测试通话听起来反应慢。我在真实的测试通话里比较了各个模型的响应速度，最后留下了更快的 GPT-4.1，没有用纸面上看起来更好的新模型。在电话里，一停顿就像是线路断了。

## 成果

- 已具备试点条件：商家坐下来一次就能完成注册、配置 agent，并在测试通话里听到效果；首个市场是餐厅。
- 一个 agent 同时处理英语和普通话。
- 预约、改约、取消和订座都能在通话中完成，不需要人工介入。

## 如果重来

先做一个通话重放工具。如果能离线把录好的通话拿出来，对着新版本的 prompt 或工具重放一遍，就能省下好几天打测试电话的时间。以后做任何语音产品，我都会从这一步开始。
