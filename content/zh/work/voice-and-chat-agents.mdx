## 背景

一家运动服饰制造商有几千家俱乐部客户，每天都在回答同样的问题：我的订单到哪了？做一套队服要多少钱？能不能找人聊聊赞助？销售和客服在邮件、电话和网页聊天之间手动回复，线索也常常在系统之间丢掉。

## 约束

- **答案必须是真的。** 订单状态来自运营系统，不能靠模型想象。
- **现有工具不换。** CRM、订单系统和邮件系统都不会动，agent 必须围绕它们来做。
- **没有专门的平台团队。** 等我转去做下一件事之后，非工程人员也得能看懂、能修改这些集成。

## 我的角色

我设计了对话流程，搭建了这些 agent，并负责它们和业务系统之间那层集成的开发与运维。队服订购表单和客户门户也是我接到这一层上的。

## 架构

- **聊天**：公开网站上的 Voiceflow agent，支持六种语言（英语、欧洲英语、西班牙语、法语、德语、意大利语），包括一个全局意图路由、基于知识库和价格表作答的产品 agent，以及独立的订单支持 agent。累计 4 万多条消息、1.5 万多名用户。
- **语音**：Retell agent 接听销售热线的来电。通话结束后，webhook 送来转写文本和摘要；工作流判断来电意图，创建或更新 CRM 线索，再连同摘要分给对应的销售。
- **集成层**：50 多个 n8n 工作流，充当 agent 和 Web 应用的 API 层。订单状态查询、销售电话预约、报价生成、审批通知和 CRM 同步，全都是由 webhook 触发的工作流。
- **纯 webhook 后端**：队服订购表单和客户门户都通过 webhook 和这一层通信，没有需要另外维护的定制 API 服务。

## 三个决策

**1. 每个事实性回答都以查询结果为准。** 聊天 agent 从不凭记忆回答“我的订单到哪了”；它会调用一个工作流去查运营数据，再返回套好模板的答案。编造订单状态原本是最大的风险，现在已经不是问题。

**2. 把集成逻辑放在业务团队看得见的地方。** n8n 里的工作流是可视化的，有版本记录，运营团队也能自己改。换成传统的服务来写，对我来说更整洁，对他们来说却是个黑箱。

**3. 按意图分配，而不是按队列排。** 语音来电在转给人之前会先分类（新线索、已有订单、赞助、其他）。每类意图都有负责人和响应时限，CRM 记录里也带着摘要，所以第一次接手的人已经心里有数。

## 成果

- 处理了 4 万多条聊天消息，服务 1.5 万多名用户。
- 每通销售来电挂断后几秒内，就会变成一条带转写文本、摘要和负责人的 CRM 记录。
- 50 多个生产工作流，在各系统之间承载订单状态、预约和审批。

## 如果重来

更早引入评估。上线之后，我才开始每周抽查 agent 的对话记录；如果从第一周就做带评分的抽样，能更早发现两个有问题的流程。我还会从第一天就接好真正的人工转接：后来一次审计发现，机器人告诉客户信息已经转交，而背后的工单流程其实是断开的。另外，我会把 webhook 校验和重试集中到一个共享库里，而不是每个工作流各写一套。
