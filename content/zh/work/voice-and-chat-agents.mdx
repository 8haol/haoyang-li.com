## 背景

一家运动服饰厂商有几千个俱乐部客户，每天都在回答同样的问题：我的订单到哪了？做一套队服要多少钱？能不能找人聊聊赞助？销售和客服要在邮件、电话和网页聊天之间来回手动回复，线索也经常在系统之间流转时丢掉。

## 难点

- **回答必须是真的。** 订单状态要从运营系统里查，不能让模型自己编。
- **现有工具一个都不换。** CRM、订单系统和邮件系统都不动，Agent 只能围绕它们来做。
- **没有专门的平台团队。** 我转去做别的项目之后，不写代码的同事也得能看懂、能改这些集成。

## 我的分工

对话流程是我设计的，Agent 是我搭的，Agent 和业务系统之间的那层集成也由我开发和维护。队服下单表单和客户门户，也是我接到这一层上的。

## 架构

- **聊天**：官网上的 Voiceflow Agent，部署在六个店面上，支持五种语言（英式和欧洲英语、西班牙语、法语、德语、意大利语）。里面有一个总的意图分流，一个根据知识库和价格表回答问题的产品 Agent，还有一个单独处理订单问题的 Agent。累计 4 万多条消息、1.5 万多名用户。
- **语音**：Retell Agent 接销售热线。通话结束后，Webhook 把文字稿和摘要送过来；工作流判断来电意图，在 CRM 里新建或更新线索，再连同摘要分给对应的销售。
- **集成层**：50 多个 n8n 工作流，相当于 Agent 和各个 Web 应用的 API 层。查订单状态、预约销售电话、生成报价、发审批通知、同步 CRM，全都是由 Webhook 触发的工作流。
- **后端只有 Webhook**：队服下单表单和客户门户都通过 Webhook 和这一层通信，不需要另外维护一个定制的 API 服务。

## 三个关键决定

**1. 凡是事实，都以实时查询为准。** 客户问“我的订单到哪了”，聊天 Agent 从来不凭记忆回答，而是调一个工作流去查运营数据，再按模板回复。原本最大的风险是模型编造订单状态，现在这个问题已经不存在了。

**2. 集成逻辑放在业务团队看得见的地方。** n8n 的工作流是可视化的，有版本记录，运营团队自己也能改。如果写成传统的后端服务，代码对我来说会更整洁，但对他们来说就是个黑箱。

**3. 按意图分配，而不是按顺序排队。** 语音来电在转给人之前，会先分成几类：新线索、已有订单、赞助、其他。每一类都有专人负责、有响应时限，CRM 记录里还带着摘要，所以接手的人第一次联系客户时就已经心里有数。

## 结果

- 累计处理 4 万多条聊天消息，服务 1.5 万多名用户。
- 每通销售来电挂断后几秒钟，CRM 里就会多出一条带文字稿、摘要和负责人的记录。
- 50 多个线上工作流，在各个系统之间处理订单状态、预约和审批。

## 复盘

评估应该更早做起来。上线之后，我才开始每周抽查 Agent 的对话记录；如果第一周就按评分标准抽样，能更早发现两个有问题的流程。转人工也应该从第一天就真正接通：后来一次检查发现，机器人告诉客户“已经帮你转给同事了”，背后的工单流程其实是断的。另外，Webhook 的校验和重试应该统一放进一个共享库，而不是每个工作流各写一套。

## 技术栈

Voiceflow、Retell、Zoho CRM、n8n、Node.js、Resend、React。
